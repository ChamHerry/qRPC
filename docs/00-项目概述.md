## 1. 项目名称与释义

**qRPC**（暂定名）。

- 字面释义：**QUIC RPC** —— 基于 QUIC 传输的远程过程调用框架。
- 递归缩写（致敬 gRPC = gRPC Remote Procedure Calls 的命名传统）：**qRPC = qRPC Remote Procedure Calls**。
- 别名释义：**Quick RPC**，呼应 QUIC 词源（QUIC = Quick UDP Internet Connections）。

> 命名为暂定，正式开源前需核查 GitHub / crates.io / npm / 域名 撞名情况。

## 2. 项目背景与立项依据

### 2.1 现状：QUIC 原生 + 全语言的 RPC 是真实空白

通过对主流 RPC 框架的调研，得到如下市场地图：

| 框架 | 原生 QUIC | 全语言 | 传输抽象 | 缺口 |
|---|---|---|---|---|
| **gRPC** | ❌（走 HTTP/2；HTTP/3 长期停滞，grpc-quic 实验性且基本停维） | ✅ 10+ 语言 | 有 | 没有原生 QUIC |
| **IceRPC**（ZeroC） | ✅ | ❌ **仅 C#/.NET**（Rust 在路上，Java/Go/Python/JS 全无） | 有 | 语言覆盖极窄 |
| **quic-rpc**（n0-computer） | ✅ | ❌ 仅 Rust（明确放弃跨语言） | 多传输 | 单语言 + 非通用 |
| **Mercury HPC / UCX** | RDMA 为主 | C 为主 | 有 | 偏 HPC，非云原生、非全语言 |

**结论**："原生 QUIC + 全语言"这个生态位，目前没有项目占据。qRPC 要填补的正是这块空白。

### 2.2 为什么 QUIC 在 RPC 场景有价值（同时也正视其代价）

- **价值**：QUIC 的 stream 独立性（消除 stream 间队头阻塞）、0-RTT、连接迁移、内置 TLS 1.3，对客户端↔服务端场景（移动 / 边缘 / IoT / 弱网）是实打实的优势。
- **代价**：QUIC 是用户态实现，在 server-to-server 高吞吐场景下 CPU 开销高于 TCP（这正是 gRPC-over-HTTP/3 长期停滞的核心原因）。
- **qRPC 的取舍**：定位为**云原生为主**，QUIC 当家，用 quinn 起步；通过传输抽象层（TAL）预留 MsQuic（高性能）与 RDMA（超低延迟）作为可插拔后端，按场景选最优传输。

## 3. 项目定位

| 维度 | 定位 |
|---|---|
| 生态方向 | **云原生为主**（对标 gRPC 的版图） |
| 核心传输 | **QUIC 当家**（quinn 起步，可换 MsQuic） |
| 杀手锏 | **全语言**（Rust / Python / Go 首发，可扩展） |
| 高端后端 | RDMA（第二阶段，锦上添花） |
| 长期愿景 | 通用全场景，对标 gRPC；同时以多传输抽象覆盖 HPC/AI 近场场景 |

## 4. 项目目标

### 4.1 短期目标（0.1 "端到端打通"）
- 内核（Rust）+ C ABI + 三语言绑定（Rust / Python / Go）+ protoc 代码生成插件端到端跑通。
- 支持四种调用模式、错误/超时/取消/背压、跨语言互通。
- 提供跨语言示例与快速上手文档，能让早期用户真正用起来。

### 4.2 中期目标（0.2 ~ 1.0）
- 0.2：接入 MsQuic 后端（验证传输抽象可换）、性能优化与 benchmark、拦截器与基础负载均衡。
- 0.3：扩展语言（Node / C++ / Java）、datagram 协同通道、健康检查/反射、可观测性完善。
- 1.0：**冻结 C ABI**，达成生产就绪（健壮性、安全、文档、稳定 API 公开承诺）。

### 4.3 长期目标（2.0+）
- RDMA 后端 + 零拷贝序列化（Cap'n Proto codec），覆盖 AI/HPC 近场超低延迟场景。
- TCP 降级后端，提升可用性与连通性。

## 5. 项目范围

### 5.1 0.1 范围内（In）
- QUIC 传输（quinn）、自研 RPC 帧协议、四种调用模式。
- Rust / Python / Go 三语言绑定与 protoc 插件。
- 错误（gRPC 兼容状态码）、超时、取消传播、背压。
- TLS 1.3 + 可选 token 鉴权、最小 tracing。

### 5.2 0.1 范围外（Out，及对应阶段）
- MsQuic 后端 → 0.2
- RDMA 后端 + 零拷贝 codec → 2.0
- datagram 协同通道 → 0.3
- 拦截器框架、客户端负载均衡、服务发现、健康检查、反射 → 0.2 ~ 0.3
- 更多语言（Node / C++ / Java …）→ 0.3 起

详见 `07-路线图与里程碑.md`。

## 6. 关键技术决策摘要

| 决策项 | 选择 | 核心理由 |
|---|---|---|
| 内核语言 | **Rust** | 内存安全（RPC 是安全敏感区）+ 现代开发效率 |
| 跨语言机制 | **C ABI（extern "C"）+ 各语言薄绑定** | gRPC C-core 验证过的架构；稳定契约，内核可自由迭代 |
| Rust 绑定 | **绕过 C ABI 直连内核** | 内核选 Rust 的隐性福利，Rust 为一等公民 |
| QUIC 栈（首发） | **quinn** | 纯 Rust、async 原生、syscall 开销低、贴合"小包高 RPS"基本盘 |
| QUIC 栈（可选） | **MsQuic**（0.2） | 峰值吞吐 / OS offload / 全语言 C ABI 友好 |
| 传输架构 | **统一传输抽象层（TAL）**，可插拔后端 | 一套 RPC 语义，按场景选 QUIC / RDMA / TCP |
| IDL / 序列化 | **复用 protobuf + 内部 Codec 抽象** | 最大生态红利、protoc 全语言覆盖；为 RDMA 零拷贝预留 codec |
| 调用映射 | **每个 RPC = 一个 QUIC bidirectional stream** | 与 gRPC 概念一致；享受 QUIC stream 独立性 |
| 帧协议 | **自研（不走 HTTP）** | 去掉 HTTP 复杂层，简洁高效 |
| 错误模型 | **复用 gRPC 状态码** | 降低迁移成本、跨语言一致 |
| 背压 | **复用 QUIC 原生流控 + 向上传导** | 天然防 OOM |

## 7. 术语表

| 术语 | 释义 |
|---|---|
| **RPC** | Remote Procedure Call，远程过程调用 |
| **QUIC** | Quick UDP Internet Connections，基于 UDP 的现代传输协议（RFC 9000） |
| **stream（QUIC）** | QUIC 内的可靠有序字节流，一个连接上可多路复用多个，彼此独立无队头阻塞 |
| **datagram（QUIC）** | QUIC 的不可靠数据报（RFC 9221），不保证可达/顺序，低延迟 |
| **gRPC** | Google 的跨语言 RPC 框架，基于 HTTP/2 + protobuf |
| **IceRPC** | ZeroC 的 QUIC 时代 RPC 框架（当前仅 C#） |
| **protobuf** | Protocol Buffers，Google 的 IDL + 二进制序列化格式 |
| **IDL** | Interface Definition Language，接口定义语言 |
| **stub** | 桩代码，由 IDL 生成的客户端/服务端接口代码 |
| **TAL** | Transport Abstraction Layer，传输抽象层（本项目自定义） |
| **C ABI** | C 应用二进制接口，跨语言调用的稳定契约 |
| **RDMA** | Remote Direct Memory Access，远程直接内存访问，内核旁路、超低延迟 |
| **FFI** | Foreign Function Interface，外部函数接口（跨语言调用机制） |
| **PyO3** | Rust ↔ Python 绑定库 |
| **cgo** | Go 调用 C 的机制 |
| **quinn** | 纯 Rust 的 QUIC 实现 |
| **MsQuic** | Microsoft 的跨平台高性能 QUIC 实现（C） |
| **deadline** | RPC 调用的超时时限 |
| **背压（backpressure）** | 消费方慢时对生产方的反压，防止内存无限堆积 |
| **队头阻塞（HoL blocking）** | 前一个数据阻塞导致后续数据被阻塞的现象 |
