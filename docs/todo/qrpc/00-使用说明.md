# qRPC 0.1 — LLM 持续实施使用说明

> 适用位置：`docs/todo/qrpc/`  
> 核心用途：让 LLM 能够在多轮会话中稳定读取状态、选择下一步、实施、验证、记录证据并恢复执行。  
> 设计原则：**任务可解析、状态可恢复、完成有证据、失败可回滚、范围可约束**。

---

## 1. 这个模板解决什么问题

普通实施方案适合人类阅读，但不一定适合 LLM 长周期执行。LLM 持续实施需要额外满足：

| 需求 | 模板约束 |
|---|---|
| 知道当前做到哪一步 | `README.md` 的 `LLM-STATE` 块记录当前任务、状态、下一步 |
| 能自动选择下一项任务 | `01-实施计划.md` 使用稳定 `T-###` 任务队列和依赖关系 |
| 不重复做已完成工作 | 每个任务有 `Status`、`Evidence`、`CompletedAt` |
| 不随意扩大范围 | 每个任务必须声明 `Files`、`Out of Scope` |
| 完成后能证明 | `02-实施状态与验证.md` 使用 `C-###` 命令记录和验收覆盖 |
| 失败后能恢复 | 每次失败记录 blocker、尝试、下一恢复动作 |
| 调研结论可复用 | `01-实施计划.md §2.4` 固化官方文档、GitHub 开源实现与采用/拒绝理由 |
| 调用链分析可追踪 | `01-实施计划.md §3` 记录目标调用链、数据流、配置流、错误流 |
| 每个任务实时校准 | `T-###` 执行前必须重新确认当前代码、候选文件、调用链是否仍匹配 |
| 人类仍能审查 | README 保留摘要、风险、验收和交付物视图 |

> **本项目说明：** qRPC 0.1 是**绿地项目**（从零搭建），故"当前调用链/代码校准"针对的是**已写出的代码**与**目标设计**（`docs/`）的一致性，而非遗留系统。

## 3. LLM 执行协议

### 3.0 实施方案生成前（中大型任务必做）

调研已在方案制定阶段完成（见 `01-实施计划.md §2.4`、`docs/00-项目概述 §2 立项依据`）。后续若引入新依赖/新机制，须补调研并落盘。

### 3.1 每轮开始

LLM 开始实施前必须：

1. 读取 `README.md` 的 `LLM-STATE`。
2. 读取 `01-实施计划.md` 的任务队列。
3. 读取 `02-实施状态与验证.md` 的最新执行日志。
4. 选择第一个满足以下条件的任务：
   - `Status = todo` 或 `Status = blocked` 且有恢复动作；
   - 所有 `DependsOn` 都是 `done` 或 `skipped`；
   - 当前任务文件范围在 `allowed_scope` 内；
   - 执行前实时校准通过：相关文件/设计仍一致、计划未落后于代码。
5. 如实时校准发现计划已过期，先更新 `01-实施计划.md §13` 和 `02-实施状态与验证.md §8`，再实施。
6. 将 `README.md` 的 `current_task` 更新为该任务。

### 3.2 每个任务实施中

每个 `T-###` 任务必须遵循：

```text
读取任务 -> 确认依赖 -> 实时校准代码/设计 -> 限定文件范围 -> 实施最小切片 -> 运行该任务验证 -> 写执行日志 -> 更新任务状态
```

禁止：

- 没有证据就把任务标记为 `done`。
- 跳过依赖任务直接实施下游任务。
- 修改 `Files` 之外的文件且不记录变更原因。
- 只写"已完成"，不写文件、命令、测试或日志证据。
- 遇到失败后反复尝试同一种方法而不记录 blocker。

> **本项目附加红线（来自全局准则）：**
> - 代码注释全部使用中文。
> - 不得用环境变量作为配置参数（用配置对象/配置项）。
> - 不得跳过依赖任务；不得伪造验证结果；不得删除失败测试。

### 3.3 每轮结束

LLM 停止前必须更新：

1. `README.md`：`LLM-STATE`、当前状态、下一步。
2. `01-实施计划.md`：当前任务状态、证据、完成时间。
3. `02-实施状态与验证.md`：命令结果、失败原因、验收覆盖。

## 4. 状态枚举

### 4.1 功能状态
```text
todo | in_progress | blocked | partial | done | rolled_back | cancelled
```

### 4.2 任务状态
```text
todo | in_progress | blocked | done | skipped
```

### 4.3 验证状态
```text
not_run | pass | fail | partial | skipped
```

### 4.4 最终 VERDICT
```text
VERDICT: PASS | VERDICT: FAIL | VERDICT: PARTIAL
```

## 5. ID 规范

| 类型 | 格式 | 用途 |
|---|---|---|
| 需求 | `R-001` | 功能需求（映射 SRS 的 FR） |
| 决策 | `D-001` | 关键技术/产品决策（含 9 项已通过决议） |
| 任务 | `T-001` | LLM 可执行任务（T-001~T-018） |
| 命令 | `C-001` | 验证命令或检查 |
| 风险 | `RK-001` | 风险与回滚项（RK-001~RK-007） |
| 问题 | `B-001` | blocker 或失败项 |
| 后续 | `NEXT-001` | 非当前范围后续事项 |

## 6. 证据规范

"完成"必须绑定至少一种证据：

| 证据类型 | 示例 |
|---|---|
| 代码路径 | `core/src/frame/codec.rs:encode` |
| 测试文件 | `core/src/frame/codec.rs::tests::encode_decode_roundtrip` |
| 命令 | `cargo test -p qrpc-core frame` |
| 接口 | C ABI `qr_call_send` |
| 配置 | 默认端口 7000、消息上限 4 MiB |
| 官方文档 | `quinn docs: bi-stream API` |
| GitHub 参考 | `n0-computer/quic-rpc: borrowed multi-transport pattern, rejected cross-lang scope` |

不要写：
```text
Status: done
Evidence: 已完成
```
应该写：
```text
Status: done
Evidence: `core/src/frame/codec.rs:encode` 黄金样本往返一致；`cargo test -p qrpc-core frame` 通过，C-001。
```

## 7. 与 docs/ 设计文档的关系

| 文档 | 作用 |
|---|---|
| `docs/`（00~07，已定稿） | 设计权威：SRS/HLD/LLD/协议规范/CABI契约/测试/路线图 |
| `docs/todo/qrpc/`（本目录） | LLM 执行控制台：状态、任务、执行证据、复盘 |

规则：

1. 设计以 `docs/` 为准；本目录 04-设计方案 仅作指针。
2. 实施中若发现设计需调整，先在 `01 §13` / `02 §8` 记录偏差，再同步 `docs/`，不得静默偏离。
3. 9 项已通过设计决议（端口 7000、COMPRESSED/SETTINGS 不进 0.1、消息上限 4 MiB、client-streaming 结束信号、metadata 平行数组、连接级回调分离、handler 按 service、无同步阻塞变体）为实施硬约束。
